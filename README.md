# LLM Testing Framework

A lightweight GenAI testing framework built with **Playwright, JavaScript, and Ollama** to validate the quality, reliability, safety, and performance of responses generated by a locally hosted Large Language Model (LLM).

The project demonstrates how traditional software testing practices can be applied to LLM-based applications using automated API tests, rule-based response evaluation, repeated-run reliability checks, and JSON reporting.

## Key Features

- **LLM API Testing:** Send prompts to a locally running Ollama model and validate responses.
- **Response Quality Evaluation:** Check expected keywords, missing keywords, response length, and rule-based quality scores out of 100.
- **Grounding Validation:** Verify whether the model answers questions using supplied context and acknowledges missing information.
- **Instruction-Following Tests:** Validate response formatting, bullet-point counts, and relevance.
- **Safety Baseline Testing:** Check refusal behavior for a harmful request and validate empty-prompt handling.
- **Reliability Testing:** Repeat prompts and measure how consistently the model produces expected results.
- **Performance Measurement:** Calculate average response latency.
- **JSON Reporting:** Save execution metrics and individual quality-evaluation results.
- **HTML Dashboard:** Generate a browser-readable dashboard from the execution metrics.
- **Environment-Based Configuration:** Configure the Ollama server URL and model through a `.env` file.

## Prerequisites

Install the following before running the framework:

- Node.js and npm
- Ollama for local model execution
- The `llama3.2:1b` model
- Git (optional, for version control)

## Installation and Setup

### 1. Clone the repository or open the project directory

```bash
git clone <your-repository-url>
cd llm-testing-framework
```

If the project is already on your machine, open its root directory instead.

### 2. Install dependencies

```bash
npm install
```

### 3. Install and prepare Ollama

Download Ollama from [https://ollama.com](https://ollama.com).

Pull the model:

```bash
ollama pull llama3.2:1b
```

Verify the model is available:

```bash
ollama list
```

If Ollama is not already running, start it using the appropriate command for your operating system. On Windows, the Ollama desktop application can run the local server.

Verify the API is reachable at `http://localhost:11434`.

### 4. Configure environment variables

Create a `.env` file in the project root:

```dotenv
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=llama3.2:1b
```

The framework uses these variables to configure the Ollama endpoint and model.

**Security:** Never commit `.env` files containing secrets. Keep `.env` listed in `.gitignore`.

### 5. Run the test suite

Run all Playwright tests:

```bash
npx playwright test --reporter=list
```

Run a specific test file:

```bash
npx playwright test tests/llm-response.spec.js --reporter=list
```

Run the repeated-request reliability test:

```bash
npx playwright test tests/llm-reliability.spec.js --reporter=list
```

Run the grounding tests:

```bash
npx playwright test tests/llm-grounding.spec.js --reporter=list
```

Run the safety tests:

```bash
npx playwright test tests/llm-safety.spec.js --reporter=list
```

## Reporting

### Playwright JSON Report

The Playwright configuration generates a JSON report at:

```text
reports/llm-test-report.json
```

### Execution Metrics Report

The reliability test generates:

```text
reports/llm-metrics.json
```

Example:

```json
{
  "generatedAt": "2026-10-18T03:58:14.485Z",
  "total": 5,
  "passed": 5,
  "failed": 0,
  "passPercentage": 100,
  "averageLatencyMs": 374.82,
  "qualityScores": []
}
```

The values above are an example of a previous test run, not guaranteed results for a future execution.

### Quality Reports

Individual response-evaluation reports can be saved under `reports/`, for example:

```text
reports/LLM-001-quality.json
reports/LLM-002-quality.json
reports/LLM-003-quality.json
```

These reports contain quality scores and missing-keyword information for their respective test cases.

### HTML Dashboard

Generate the HTML dashboard:

```bash

```

Open the generated file:

```text
reports/llm-dashboard.html
```

The current dashboard reads `reports/llm-metrics.json`. Individual quality reports are stored separately, so their scores will appear on the dashboard only after the report integration is implemented.

## Quality Scoring Approach

The current rule-based scoring system awards up to 100 points:

| Criterion | Weight |
|---|---:|
| Non-empty response | 30 |
| Expected keyword coverage | 40 |
| Response within the configured length limit | 30 |
| **Total** | **100** |

This score measures compliance with predefined rules, not general intelligence or factual correctness.

For stronger evaluation, additional checks could include semantic similarity, factual consistency, context relevance, and human-reviewed reference answers.

## Performance and Reliability

The reliability test submits the same question multiple times and records whether each response contains the expected keyword.

The framework calculates:

- Total requests
- Passed and failed evaluations
- Pass percentage
- Average response latency

Latency depends on the local machine, model size, prompt length, model warm-up, and system load. Results from a small number of requests should not be treated as production performance guarantees.

## Limitations

- The initial framework uses a small local model, which may not consistently follow complex instructions.
- Keyword-based assertions can miss semantically correct responses or accept incorrect ones.
- Refusal-language checks are a basic safety baseline, not a comprehensive safety evaluation.
- Rule-based scores do not establish factual accuracy.
- Local response latency does not represent hosted or production inference performance.
- The current HTML dashboard reads the metrics report; combining all individual quality reports remains a potential enhancement.
